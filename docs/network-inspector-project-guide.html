企业局域网网络巡检与故障诊断工具

这是一个面向 IT 技术支持 / 网络支持 / 运维实习生 场景的网络巡检项目。 它不是单纯把 ping 和 traceroute 做成网页，而是把 ICMP 连通性、DNS 可用性、端口识别、路由探测、批量巡检、规则诊断、历史记录、报告导出 组合成一个结构化的小型巡检平台。

项目定位 企业网络巡检 + 故障辅助诊断
适用岗位 IT 支持 / 网络支持 / 运维实习
运行入口 streamlit run app.py
核心特征 多信号判断，而不是只看 ping

1. 项目背景

为什么要做这个项目

IT 技术支持岗位的真实工作并不只是“修电脑”，还包括网络连通性排查、终端与服务访问问题定位、 资产对象批量巡检、故障记录沉淀和标准化输出。传统终端命令虽然能查数据，但难以形成可复用的巡检流程。

这个项目解决什么痛点

把散落的命令和操作流程统一收进一个网页工具里，让巡检从“手工临时排查”变成 “带对象角色、带历史记录、带诊断结论、可导出报告”的半自动流程。

你可以把这个项目理解为：为企业办公网、服务器区、实验室或分支机构做的一套轻量级网络巡检与故障辅助诊断平台。

2. 项目是做什么的

单主机诊断 对一个 IP 或域名执行 ICMP、DNS、Nmap 端口识别和路由追踪。
批量巡检 按企业对象模板批量扫描网关、交换机、打印机、NAS、Web 站点等。
局域网扫描 通过 ARP 探测当前二层网段在线设备，形成本地局域网资产感知。

用户最终能得到什么

  • 目标是否在线，不再只看 ping，而是综合多个信号判断。
  • DNS 是否可用、响应是否正常。
  • 开放端口与服务识别结果。
  • 是否能拿到路由路径信息。
  • 自动生成的“诊断结论”和“建议动作”。
  • 历史扫描记录，以及可下载的 Markdown / CSV 报告。

3. 核心入口是什么

运行入口

项目主入口是根目录的 app.py。启动命令是： 

streamlit run app.py
入口职责

app.py 负责加载页面、初始化数据库、组织单主机诊断 / 批量巡检 / 局域网扫描 / 历史记录四个功能页， 同时承接报告下载和手动保存逻辑。

入口文件 职责 你可以怎么解释
app.py 页面组织、表单输入、结果展示、数据库初始化、会话状态管理 “我把前端交互、扫描触发、结果展示和导出入口都统一放在这里。”

5. 各个模块的作用是什么

模块 / 文件 作用 关键点
app.py 项目总入口、页面渲染、表单处理、报告下载与保存 四个标签页：单主机诊断、批量巡检、局域网扫描、历史记录
scanners/icmp_ping.py 用 Scapy 发 ICMP 探测包，统计时延和丢包率 给出 sent / received / avg_ms / loss_rate
scanners/dns_check.py 用 Scapy 发 DNS 查询包，测试指定 DNS 服务器解析能力 适合区分“主机不回 ping”和“DNS 服务仍可用”这两种情况
scanners/nmap_scan.py 调用 Nmap 做端口扫描和服务识别 支持自动发现 Windows 常见安装路径，减少 PATH 问题
scanners/trace_route.py 调用 Nmap traceroute 获取跳数信息 用于辅助判断目标是否存在路径可达迹象
scanners/arp_scan.py 扫描当前二层局域网在线设备 适合办公网段、实验室网段的本地资产发现
services/diagnostic_service.py 扫描编排层 把多个 scanner 串起来，并做异常兜底
services/diagnosis_rules.py 规则引擎 把原始探测结果转成“在线 / 服务在线 / 路径可达 / 离线”
services/target_templates.py 批量巡检模板 内置办公网、服务器区、分支机构、实验室等企业场景
services/report_service.py 报告构建与保存策略 默认只在内存生成报告，手动保存时按日期分层并执行清理策略
db/schema.sql + db/repo.py SQLite 存储层 把扫描记录沉淀成可查询的历史数据

6. 一次扫描的完整链路

  1. 用户在网页中输入目标、DNS 服务器、测试域名、对象角色等参数。
  2. app.py 调用 run_host_diagnostic() 或 run_batch_diagnostic()。
  3. diagnostic_service.py 依次执行：
    • ping_stats()：测试 ICMP 连通性
    • dns_check()：测试 DNS 解析
    • scan_ports()：测试开放端口和服务识别
    • trace_route()：测试路径信息
  4. diagnosis_rules.py 根据结果生成状态、结论、建议。
  5. db/repo.py 把扫描结果写入 SQLite。
  6. report_service.py 在内存中构造 Markdown / CSV 报告文本。
  7. 页面展示诊断结果，并允许用户下载或手动保存本地报告。
表单提交
  -> run_host_diagnostic()
     -> ping_stats()
     -> dns_check()
     -> scan_ports()
     -> trace_route()
     -> analyze_host_result()
  -> save_host_scan()
  -> build_host_report_bundle()
  -> 页面展示 + 下载 / 手动保存

7. 多信号判定与诊断结果是怎么实现的

这里不是机器学习，也不是复杂 AI，而是一个规则引擎。规则引擎更适合这个项目，因为网络诊断要求可解释、可复现、便于面试说明。

状态 判定逻辑 解释
在线 ICMP 有回包 说明主机在网络层直接响应探测
服务在线 ICMP 不通，但端口开放或 DNS 服务成功 适合识别“禁 ping 但业务还活着”的目标
路径可达 ICMP 不通、端口没有明显结果，但 traceroute 有路径 说明路径上仍有到达迹象
离线 ICMP、端口、DNS、路径都没有提供可达证据 更接近真正不可达或被策略阻断

这部分是项目最有“工程价值”的地方。它把终端命令结果提升成了 结构化诊断，这也是你和“只会敲 ping 命令”的区别。

为什么要这么设计

  • 很多公网 DNS、云服务、边界设备会禁用 ICMP。
  • 如果只看 ping，会把“服务可达”的目标误判为离线。
  • 多信号判定能更接近企业真实故障排查逻辑。

9. 报告与存储策略

SQLite 持久化

每次扫描默认会写入 SQLite 数据库 data/network_inspector/inspector.db，这样历史记录能够长期保留并在页面里回看。

报告导出策略

报告默认只在内存中生成，不自动写入 reports/。只有用户点击“保存 Markdown + CSV 到本地报告目录”时才真正落盘。

为什么这样改

  • 避免每次测试都在 reports/ 里生成大量重复文件。
  • 把“历史记录”和“归档报告”两种诉求分开处理。
  • 更贴近企业系统的“数据库为主，文件归档为辅”思路。

当前保存策略

  • 按日期分层保存到 reports/YYYY-MM-DD/
  • 默认保留最近 30 天
  • 默认最多保留最近 100 份报告组

这一点在面试里很好讲：你不仅做了扫描，还考虑了数据沉淀策略、报告生命周期和目录膨胀问题。

11. 如果你要把它讲得像自己做的，可以怎么说

一句话版本

我做了一个基于 Python、Scapy、Nmap、Streamlit 和 SQLite 的企业网络巡检与故障辅助诊断工具， 可以对单主机、批量企业对象和局域网设备做诊断，并且通过多信号规则判断目标是真离线、服务在线还是路径可达。

面试时建议按这 5 个点讲

  1. 为什么做：IT 支持岗位不仅需要会敲命令，还需要把排障过程标准化、可视化、可复盘。
  2. 做了什么：把 ping、DNS 测试、端口识别、路由追踪、ARP 扫描、批量巡检、历史记录和报告导出整合成一个 Web 工具。
  3. 技术亮点：不是只看 ICMP，而是设计了多信号诊断规则，避免把“禁 ping 但服务可达”的目标误判成离线。
  4. 工程化点：引入 SQLite 存储、企业场景模板、批量巡检、报告生命周期管理。
  5. 后续还能做什么：接 SNMP、定时巡检、异常告警、资产台账联动。

可以主动强调的技术决策

  • 选择 Streamlit 是为了快速做出可用页面，把重点放在诊断逻辑而不是前端框架搭建。
  • 选择规则引擎而不是机器学习，是因为网络诊断要求强解释性和可复现性。
  • 默认只入库、不自动落盘，是为了避免报告目录膨胀，提升长期可维护性。

12. 后续更改建议

优先级高：接入 SNMP

把交换机、AP、打印机、NAS 的接口流量、CPU、内存、在线状态纳入巡检。这样项目会更贴近网络支持岗位。

优先级高：定时巡检与趋势图

增加定时任务，把每天的时延、丢包率、端口变化做成趋势图，而不是只看某一次结果。

优先级中：对象信息入库更完整

目前 SQLite 里还没有完整保存 object_label、object_role 等企业语义字段，这会影响历史记录回放的完整性。

优先级中：异常告警联动

可以接企业微信机器人、邮件或工单系统，遇到异常目标时自动推送或生成工单。

优先级中：预期端口 / 角色规则

给不同角色定义预期端口和基线规则，例如打印机应暴露 80/9100，DNS 服务器应暴露 53。

优先级低：前端交互增强

例如网络拓扑视图、异常热力图、保存的报告管理页，让页面更像一个完整平台。

当前项目最值得你记住的两个“已知限制”是： 历史记录回放时对象角色信息还原不完整， 以及 ICMP / traceroute 的结果受目标策略和本机权限影响较大。 这两个限制不影响项目价值，反而是你可以主动说明自己理解边界的地方。
